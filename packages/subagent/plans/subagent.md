# Persistent subagents

**The Job** — Add a focused general-purpose subagent extension to this monorepo, with persistent worker conversations and live progress.
**The Why** — `build-feature` Orchestrator mode needs parallel phase workers that retain context across fresh review rounds; the installed example cannot continue workers.
**The Guardrail** — Keep phase dependencies, PRs, verification policy, merges, and Git worktree ownership in the orchestrator/skill. Preserve the existing footer and session-board.
**Done means** — An orchestrator can start isolated workers, wait without polling, message the same worker across review rounds, run fresh reviewers, inspect progress, stop children, and explicitly recover saved conversations after shutdown or reload.

## Decisions
- **Interview depth** — Key decisions only.
- **Build mode** — Solo (user selected). Fresh reviewer subagents use `gpt-6-astra-fast`, matching the parent model, through a dedicated profile; effort comes from the agent definition because the installed spawn tool has no effort override. Keep the installed subagent tool unchanged during bootstrap.
- **Scope** — A focused general-purpose extension in this repository. Profiles, start/message/wait/stop controls, parallel children, and progress UI; no built-in feature workflow engine.
- **Worker lifetime** — Live workers with saved recovery. Use `lifetime: "retained"` for phase workers: keep one RPC child across rounds until explicitly stopped. Default `lifetime: "once"` suits simple tasks and fresh reviewers: persist the terminal result, then automatically close the child process on success or failure. Retirement never changes a successful result to interrupted. Only retained workers support later tasks and recovery. Stop all owned children safely on shutdown/reload; no detached unattended workers. One-shot retirement is the approved review fix.
- **Progress UI** — Compact persistent panel near the editor plus `/subagents` inspector with live output and message/stop controls. Do not replace the footer.
- **Worktree ownership** — The orchestrator creates and retains phase worktrees and supplies `cwd`. The extension does not create branches, merge, or remove worktrees.
- **Runtime support** — Pi provides long-lived RPC children, event streams, steering/follow-up, and persisted sessions. Existing session-board registers TUI sessions only, so child progress needs its own surface. `research`
- **Package identity** — `@lwlee2608/pi-subagent` in `packages/subagent`, matching monorepo packaging. `agent`
- **Public API** — One `subagent` tool with `start`, `message`, `wait`, `status`, `stop`, `recover`, and `reply` actions. `start` returns after admission with a stable worker ID and initial run ID, not after task completion. `wait` supports one/any/all selected runs without polling. `/subagents` opens the inspector. The action contract below is authoritative.
- **Run identity and messages** — Keep worker/conversation identity separate from each task. An idle retained worker accepts `message` in `task` mode and returns a new run ID. A running worker accepts only `steer` mode, which modifies its current run and keeps that run ID. Reject new tasks while a worker is queued, working, or blocked; reject steering unless working. A blocked question uses `reply`, keeping its run ID. Do not queue independent follow-up tasks in v1. Starting independent workers always creates fresh context, not a parent fork. Busy-message semantics are the approved review fix.
- **Resource inheritance** — Inherit skills and project instructions, but explicitly select child extensions, including required model providers. Do not blindly load parent UI or orchestration extensions.
- **Profiles and tool restrictions** — Compatible Markdown profiles from `~/.pi/agent/agents`, with bundled worker/reviewer fallbacks and explicitly enabled trusted project profiles. Preserve the existing reviewer, including bash for Git/gh inspection. Read-only is an instruction-based contract, not an OS sandbox.
- **Model and effort selection** — Explicit model and effort start options, validated against available provider/model support. Resolve call override, then profile, then current parent configuration; preserve the resolved selection for recovery. No silent model fallback. `agent`
- **Child boundary** — Disable nested delegation. Use standard Pi CLI/RPC and persisted Pi sessions rather than another agent runtime. Load extensions from an explicit user-controlled allowlist, with profile-level selection only from that list. Missing provider/tool setup fails visibly. Profile paths and launch contracts are resolved before spawning. `agent`
- **Child questions** — Provide a child-to-parent question channel. Mark the child blocked and release the parent's wait. The parent answers or asks the user before continuing the same worker.
- **Cancellation** — Cancelling a wait cancels only that wait. Workers keep running until explicitly stopped or the parent shuts down/reloads. Stop clears queued messages, aborts active work, and closes the process with bounded escalation. Never roll back or delete worktree changes.
- **Recovery scope** — Only the original parent Pi session may explicitly recover its saved workers. Enforce exclusive ownership, preserve saved cwd/model/profile settings, and reject missing or changed recovery prerequisites rather than guessing. No adoption into another parent session.
- **Recovery behavior** — Stop closes the worker and marks only an unfinished run interrupted; preserve all already-terminal results. Recovery reopens a retained conversation in a new RPC process under the same worker ID and leaves it idle. A subsequent explicit task gets a new run ID; never automatically replay an interrupted task, steer, or reply. If process ownership is uncertain, refuse recovery until resolved. Session shutdown, reload, and replacement all release owned processes. `agent`
- **Question lifetime** — Scope every question to its worker, run, and process generation. Stop, process exit, reload, or shutdown cancels its pending questions and unblocks waiters. Reject stale or duplicate replies. Recovery shows unresolved questions as cancelled history, never as a live tool invocation; the parent sends a new continuation task with the decision if needed. Cancellation is not permission to guess or proceed with the disputed action. This is the approved question-recovery fix.
- **UI detail** — Place a bounded, compact panel above the editor. Show task label, state, current tool, elapsed time, and provider-reported usage where available. No synthetic completion percentages. Inspector shows live transcript, model/cwd, and message/reply/stop controls. No terminal panes, footer replacement, or session-board changes. `agent`
- **Storage and limits** — Store child sessions and bounded runtime metadata under `getAgentDir()/pi-subagent/`, scoped by parent session ID, not inside worktrees. Default to four active tasks and sixteen admitted live/reserved workers per parent, both configurable. Queued workers count against the process cap; spawn only when a task slot is available. Idle retained workers do not spend active-task slots. Reject excess starts clearly, and release one-shot process reservations only after confirmed exit. Blocked runs keep their task slot, but `reply` and `stop` never require one. Pending questions from any owned child interrupt waits, even waits targeting queued siblings, so the parent can release blocked work. The numeric process cap is an `agent` default.
- **Events and results** — Settle on Pi's final lifecycle boundary rather than the first `agent_end`. Stream bounded progress; retain full persisted transcripts for inspection. Coalesce rendering, not lifecycle transitions. Report errors separately from successful idle completion. Account for child usage once, not on each repeated status/wait. `agent`
- **Child question transport** — Add a dedicated child-only question tool using a narrow parent bridge; do not load the parent's custom TUI questionnaire inside RPC children. Questions have stable IDs and explicit reply/cancel outcomes. Unexpected child UI permission prompts must fail closed or be explicitly forwarded, never auto-approved. `agent`
- **Platform and validation** — Target the existing Node 22/Linux development environment and Pi 1.x APIs. Test with deterministic RPC fixtures and a local Pi/mock-provider integration path before paid live calls. Do not claim untested cross-platform process cleanup support. `agent`
- **Skill integration** — Include a separate change to `agent-skills/skills/build-feature/SKILL.md` with the concrete API and recovery rules. Use retained phase workers and one-shot fresh reviewers; stop workers before removing worktrees. Resume a recoverable worker in the original parent session rather than obeying the skill's current unconditional fresh-worker resume sentence. Outside that recovery scope, explicitly report a fresh-worker restart. Keep Git changes and commits separate across repositories.
- **Installation** — Never load both this package and the existing local example: both register `subagent`. Preserve agent Markdown files, disable the old extension reversibly, configure the required provider allowlist, and verify exactly one active tool. Use an isolated installation for development/demo; changing the user's global installation or publishing requires separate approval. Follow the rollout/rollback procedure below.
- **Demo** — Disposable parallel orchestration with live model calls, then user confirmation of Pi UI. Use temporary Git worktrees, a fresh reviewer, feedback to the original worker, and explicit saved recovery. No GitHub PRs or deployment.
- **Phase count** — Four sequential phases, selected by the user: persistent tasks with live status; parallel workers and questions; saved recovery; full inspector and skill integration. Each phase changes the shared lifecycle/API, so there are no parallel implementation phases.

## Action contract

IDs are opaque, validated, and scoped to the original parent session. Invalid arguments fail before spawning or sending input. Serialize each worker's lifecycle mutations, including inspector actions. Never wait while holding the mutation lock needed for replies or stop.

| Action | Input and behavior |
| --- | --- |
| `start` | `agent`, `task`, optional `label`, `cwd`, `model`, `effort`, `lifetime` (`once` default or `retained`), and `agentScope` (`user` default; trusted project opt-in). Return `workerId`, `runId`, and admitted state. Missing `cwd` uses the parent cwd. Admission is not successful task completion. |
| `message` | `workerId`, `message`, and `mode` (`task` default or `steer`), with optional `label` for a new task. Task mode requires an idle retained worker and creates a new run. Steer mode requires a working child and retains the current run. Treat task/guidance text as literal input, not slash-command dispatch. Report acceptance separately from execution success; an unexpected handled disposition is not a completed task and must not leave a waiter hanging. No queued independent follow-ups. |
| `wait` | Nonempty `runIds`, `mode` (`all` default or `any`), and optional positive `timeoutMs`. One ID is a single-run wait. Return when the selected completion condition holds, any owned question needs attention, or the wait window expires. Default window: 30 minutes; expiry is not task failure. Return explicit reason, selected-run snapshots, terminal results, and pending question IDs. Await events, not status polling. Cancellation removes only this waiter. |
| `status` | Optional `workerId`; omit to list this parent's workers, run IDs, states, and pending questions. Include bounded current activity/result summaries and references to full persisted output. It does not start work or consume a result. |
| `reply` | `questionId` and exactly one of `message` or `cancelled: true`. Only the current process generation may consume it. Return delivery acknowledgement, not task completion. Cancelling an unresolved decision interrupts the run rather than granting permission to continue. |
| `stop` | `workerId`. Cancel queued work/questions, stop owned execution, and confirm process exit or report cleanup failure. Idempotent; keep session files and terminal results. Never remove a worktree or roll back edits. |
| `recover` | `workerId` of a closed/interrupted retained worker owned by the same parent. Acquire exclusive ownership, verify saved launch prerequisites, reopen its session, and return idle without model work. Reject live, one-shot, foreign, or uncertain-ownership targets. |

`agent_settled` completes a run only after accepted input and final outcome checks. Subscribe before dispatch, retain early events until acceptance is known, and distinguish launch/provider failures from success. Steering cannot create a second completion record. A wait on an old run always returns that run's immutable result, never a later run on the same worker. Multiple waiters do not duplicate usage accounting.

Worker states include queued, working, blocked, idle, and closed; terminal run outcomes are completed, failed, or interrupted. A closed one-shot worker can still have a completed run. Report model/tool restrictions as capabilities, not an OS sandbox.

## Implementation boundaries

- Separate lifecycle/state, RPC/process infrastructure, persistence, tool adapter, and presentation. Use Pi's typed RPC protocol; reuse exported helpers where they meet the required event, UI-response, cancellation, and process-exit contracts. Do not access private client fields to build the question bridge.
- Match sibling package conventions: ESM TypeScript source, Node tests, `tsc --noEmit`, host packages as `*` peers, no bundled Pi runtime. Ship bundled profiles and the child-only question bridge; exclude tests and plans from the artifact. Load only the parent entry point through the public package manifest.
- Use an explicit user-owned package config at `getAgentDir()/pi-subagent/config.json` for child extension selection and limits. Resolve approved extension entries before spawn; reject missing entries or requested tools/providers that did not load. Preserve required model-provider extensions without inheriting parent UI extensions. Do not read credential contents to discover providers.
- Persist the resolved launch contract and session path before accepting a retained worker as recoverable. Private storage, atomic metadata updates, exclusive ownership, generation checks, and bounded cleanup prevent two processes from writing the same conversation. Failed persistence must be visible, not silently downgrade recovery.
- Guard child bootstrap with a parent-only capability so the question bridge cannot become a general cross-session control endpoint. Sanitize displayed terminal controls and bound in-memory output. Retain full transcripts privately; do not publish or upload them.
- Development uses temporary repositories, agent directories, and explicit test extensions. Automated verification uses a local deterministic Pi provider with no network or credentials, not only mocked child events. Test launch, real tools, settlement, cancellation, and process cleanup. No implementation-phase Verify is deferred to the live demo.
- This extension cannot bootstrap its own persistent orchestration before it exists. If built through `build-feature`, use Solo with the currently installed one-shot reviewer for all four phases. Do not change the global subagent tool mid-build. This bootstrap choice is `agent` guidance, not a recorded build-mode answer.
